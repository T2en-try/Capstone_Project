# Mobile UI Tasks
รวบรวมปัญหา UI บนมือถือและแนวทางการแก้ไข

---

### 1. หน้า Popup แสดงผลหลังส่งรายงานสำเร็จ ไม่มีปุ่มปิด ✅ เสร็จแล้ว
**ปัญหา:** 
เมื่อผู้ใช้งานส่งรายงานสำเร็จ ระบบจะแสดงหน้าต่าง Popup แสดงรายละเอียดและผลการวิเคราะห์ AI แต่ในหน้าจอมือถือไม่มีปุ่มสำหรับกด "ปิด" (Close) เพื่อออกจากหน้าต่างนี้ 

**แนวทางการแก้ไข:**
- ค้นหา Component ที่รับผิดชอบแสดงผลหน้า Popup หลังบ้านส่งสำเร็จ (เช่นในหน้า `/report` หรือใน `UserReportPage.jsx`)
- เพิ่มปุ่มไอคอนปิด (`CloseOutlined` จาก ant-design/icons) ไว้ที่มุมขวาบนสุดของกรอบ Modal
- หรือเพิ่มปุ่ม "ปิดหน้าต่าง" / "กลับสู่หน้าหลัก" ขนาดเต็มความกว้าง (Full-width button) ไว้ที่ด้านล่างสุดของเนื้อหาเพื่อให้ผู้ใช้งานกดปิดได้ง่ายขึ้นบนมือถือ

---

### 2. สัดส่วนการจัดวางองค์ประกอบใหญ่เกินไปและไม่สมดุล (ทุกหน้า) ✅ เสร็จแล้ว
**ปัญหา:**
สัดส่วนของ Card, รูปภาพ, Padding, และ Typography ในหน้าจอมือถือมีขนาดใหญ่เกินไป ทำให้องค์ประกอบต่างๆ กินพื้นที่หน้าจอมาก ส่งผลให้หน้าเว็บมีความยาวเกินความจำเป็น ผู้ใช้ต้องเลื่อนหน้าจอ (Scroll) ยาวมาก และทำให้ประสบการณ์การใช้งาน (UX) ทำได้ยาก

**แนวทางการแก้ไข:**
- ทำการไล่ตรวจสอบ UI ทุกหน้า (โดยเฉพาะหน้าของ User เช่น Dashboard, Report Page)
- ปรับลดขนาด Padding/Margin (`p-`, `m-`, `gap-`) ในหน้าจอขนาดเล็ก 
- ลดขนาด Font Size และขนาดความสูงของรูปภาพหรือ Container ให้อยู่ในสัดส่วนที่พอดีกับมือถือ
- พิจารณาใช้ Grid หรือ Flex layout แบบแนวนอนที่เลื่อนได้ (Horizontal Scroll) หรือจัดกลุ่มข้อมูลให้กระชับขึ้นเพื่อลดความยาวในแนวตั้ง
- ตรวจสอบการทำงานของ Breakpoints (`sm:`, `md:`) ใน Tailwind CSS หรือ Style ที่กำหนดเพื่อให้หน้าเว็บดูสมดุลทั้งจอเล็กและจอใหญ่

---

### 3. การแสดงรายการยาวเกินไป ควรใช้การแบ่งหน้า (Pagination) ✅ เสร็จแล้ว
**ปัญหา:**
การแสดงผลข้อมูลแบบรายการ (List/Feed) ในปัจจุบันเป็นการนำข้อมูลมาเรียงต่อกันลงมาเรื่อยๆ ทำให้บนหน้าจอมือถือต้องเลื่อนจอ (Scroll) ยาวมากเกินไป ซึ่งไม่สะดวกต่อการใช้งาน

**แนวทางการแก้ไข:**
- เปลี่ยนรูปแบบการแสดงผลแบบ List ยาวๆ ให้มีการทำ Pagination (แบ่งหน้า) สำหรับหน้าจอมือถือโดยเฉพาะ
- กำหนดจำนวนรายการต่อหน้า (Page Size) ให้เหมาะสม เช่น 5-10 รายการ เพื่อให้ข้อมูลพอดีกับหนึ่งหน้าจอโดยไม่ต้องเลื่อนเยอะ
- เพิ่มปุ่มหรือคอนโทรลสำหรับการเปลี่ยนหน้า เช่น "หน้าก่อนหน้า" (Previous) และ "หน้าถัดไป" (Next) หรือหมายเลขหน้า ไว้ด้านล่างสุดของรายการ
- ไล่ตรวจสอบและปรับปรุงทุกหน้าที่มีการแสดงผลแบบรายการ (เช่น หน้ารายงานของฉัน, รายการปัญหาที่แจ้ง, ฯลฯ) ให้ใช้ระบบ Pagination เหมือนกันทั้งหมด

---

### 4. ปรับโครงสร้าง Layout ให้เป็นมาตรฐานเดียวกันทุกหน้า (ทั้งผู้ใช้และเจ้าหน้าที่) ✅ เสร็จแล้ว
**ปัญหา:**
ในหน้า Dashboard และหน้ารายการต่างๆ มีการนำทุกอย่างมาแสดงรวมกันในหน้าเดียว (เช่น ฟอร์มแจ้งปัญหา, ตัวอย่างภาพ, สถิติรวม, และรายการแจ้งซ่อม) ทำให้หน้าจอยาวเกินไปและรกตา ผู้ใช้งานต้องเลื่อนลงไปไกลกว่าจะเจอข้อมูลที่ต้องการ นอกจากนี้รูปแบบของฝั่งผู้ใช้ (User) และฝั่งเจ้าหน้าที่ (Admin) ยังไม่เป็นรูปแบบเดียวกัน

**แนวทางการแก้ไข:**
- **นำมาตรฐานนี้ไปใช้กับทุกหน้า:** ใช้รูปแบบโครงสร้าง Layout ที่ปรับปรุงใหม่นี้กับ **"ทุกหน้า"** ทั้งในส่วนของ User Dashboard, Admin Dashboard, หน้ารายการของ Admin และหน้าอื่นๆ ที่มีการแสดงผลคล้ายกัน เพื่อให้ประสบการณ์การใช้งานสอดคล้องกันทั้งหมด
- **แยกส่วนการทำงาน:** ควรแยก "ส่วนกรอกฟอร์ม" และ "ส่วนแสดงข้อมูล/ประวัติ" ออกจากกัน อาจใช้ระบบ Tabs แถบเมนูด้านบน หรือทำปุ่มแจ้งปัญหาเป็นปุ่มลอย (Floating Action Button - FAB) ที่มุมจอล่างขวา เมื่อกดค่อยเปิด Modal ของฟอร์มขึ้นมาแทน
- **ซ่อนข้อมูลที่ใช้ครั้งเดียว:** ส่วนเช่น "ตัวอย่างการถ่ายภาพ" ควรซ่อนไว้ใน Accordion (กดเพื่อกางออก) หรือซ่อนหลังปุ่มไอคอน (i) Info เพื่อไม่ให้กินพื้นที่โดยไม่จำเป็น 
- **ปรับขนาดและรูปแบบ Card สถิติ:** ในส่วนของ "สถิติรวม" ให้เปลี่ยนจากการจัดแบบ Grid 2x2 เป็นรูปแบบแนวนอนที่ปัดซ้ายขวาได้ (Horizontal Scroll) หรือลดทอนลงมาให้อยู่ในบรรทัดเดียว (Compact Chips)
- **ปรับดีไซน์ Card รายการ:** เปลี่ยนปุ่ม "ดูรายละเอียด" ที่ใหญ่เทอะทะออก แล้วทำให้ "คลิกที่ตัวการ์ด" (Clickable Card) แทนเพื่อประหยัดพื้นที่ และใช้ร่วมกับ Pagination ตามข้อ 3

### 5. ปัญหาแผนที่ดูดการเลื่อนจอ (Map Scroll Trap) ✅ เสร็จแล้ว
**ปัญหา:** 
ในหน้าที่มีแผนที่ (Map) เมื่อผู้ใช้งานพยายามเลื่อนหน้าจอ (Scroll) ลงมาด้านล่าง แต่ถ้านิ้วไปโดนบริเวณพื้นที่ของแผนที่ แผนที่จะถูกเลื่อน (Pan) แทนที่จะเป็นการเลื่อนหน้าจอเว็บ ทำให้ผู้ใช้เลื่อนผ่านแผนที่ไปด้านล่างได้ลำบากมากบนมือถือ

**แนวทางการแก้ไข:**
- ปิดการเลื่อนแผนที่ด้วยนิ้วเดียวบนมือถือ (Disable single-finger dragging) และใช้การแตะ 2 นิ้วเพื่อเลื่อนแผนที่แทน
- หรือตั้งค่าให้แผนที่ไม่ตอบสนองต่อการ Scroll ในแนวตั้ง (Touch Action) เพื่อให้ผู้ใช้สามารถไถหน้าจอผ่านแผนที่ไปได้อย่างราบรื่น

---

### 6. แถบค้นหาและตัวกรอง (Filter & Search) กินพื้นที่แนวตั้ง ✅ เสร็จแล้ว
**ปัญหา:** 
ในหน้ารายการต่างๆ มักจะมีช่องค้นหา (Search input) และตัวกรองสถานะ (Dropdown) เรียงต่อกันลงมา ซึ่งทำให้เสียพื้นที่หน้าจอมือถือไปหลายบรรทัดก่อนที่จะถึงตัวเนื้อหาจริงๆ

**แนวทางการแก้ไข:**
- ยุบรวมระบบกรองข้อมูลไว้ในปุ่มเดียว เช่นปุ่มไอคอนรูปกรวย (Filter)
- เมื่อกดปุ่มกรอง ค่อยเปิดหน้าต่างแบบ Bottom Sheet (เลื่อนขึ้นจากขอบล่าง) หรือ Modal ขึ้นมาให้ผู้ใช้เลือกตัวกรอง เพื่อประหยัดพื้นที่บนหน้าหลัก

---

### 7. Popup ข้อมูลบนแผนที่ล้นออกนอกจอ (Map Popup Overflow) ✅ เสร็จแล้ว
**ปัญหา:** 
หน้าต่าง Popup รายละเอียดบนแผนที่ (เช่น ใน `MapCard.jsx` ที่มีการกำหนด `width: 320`) อาจจะมีขนาดกว้างเกินไปสำหรับมือถือรุ่นที่มีหน้าจอเล็ก ทำให้ปุ่มหรือข้อมูลบางส่วนตกขอบจอ

**แนวทางการแก้ไข:**
- ปรับความกว้างของ Popup จากค่าคงที่ (Fixed width) ให้เป็นแบบยืดหยุ่น เช่น ใช้ `width: "90vw"` หรือ `maxWidth: "320px"` เพื่อให้ Popup หดตัวตามขนาดความกว้างของจอมือถือได้ ไม่ล้นขอบ

---

### 8. กราฟ/แผนภูมิ (Chart) ไม่ตอบสนอง (Chart Responsiveness) ✅ เสร็จแล้ว
**ปัญหา:** 
ในหน้า Admin Dashboard ที่มีกราฟแท่ง (Bar Chart) หรือกราฟวงกลม (Pie Chart) พอย่อลงมาในจอมือถือ กราฟมักจะถูกบีบจนเล็ก ตำนาน (Legend) ทับซ้อนกับตัวกราฟ หรือข้อความเล็กจนอ่านไม่ออก

**แนวทางการแก้ไข:**
- ตั้งค่าความสูงขั้นต่ำ (Min-height) ให้กราฟบนหน้าจอมือถือ
- ย้ายคำอธิบายกราฟ (Legend) ไปไว้ด้านล่างสุดแทนที่จะไว้ด้านข้าง
- (สำหรับกราฟแท่ง) อาจพิจารณาเปลี่ยนเป็นกราฟแท่งแนวนอน (Horizontal Bar) บนมือถือ เพื่อให้เลื่อนดูข้อมูลได้ง่ายขึ้น

---

### 9. การทำงานของเมนูนำทาง (Sidebar / Navigation) บนมือถือ ✅ เสร็จแล้ว
**ปัญหา:** 
เมนู Sidebar ของฝั่ง Admin หากไม่พับเก็บจะกินพื้นที่จอทั้งหมด หรือถ้าพับเก็บแต่กดยากก็จะทำให้ใช้งานลำบาก ส่วนฝั่ง User การใช้ Hamburger menu (ขีด 3 ขีด) อาจเข้าถึงเมนูต่างๆ ได้ช้าและไม่ถนัดเมื่อใช้งานมือเดียว

**แนวทางการแก้ไข:**
- **ฝั่ง Admin:** ต้องมั่นใจว่า Sidebar จะถูกพับเก็บเป็น Drawer (เลื่อนออกมาจากขอบซ้ายเมื่อกดปุ่มเมนู) เมื่อแสดงบนหน้าจอมือถือ
- **ฝั่ง User:** ควรเปลี่ยนไปใช้ **Bottom Navigation Bar** (แถบเมนูด้านล่างสุดของจอ) แทนการใช้ Sidebar หรือเมนูซ่อน เพื่อให้เข้าถึงฟังก์ชันหลัก (เช่น หน้าหลัก, แจ้งปัญหา, โปรไฟล์) ได้ง่ายดายด้วยนิ้วโป้งมือเดียว

---

### 10. คีย์บอร์ดบังหน้าจอเวลาพิมพ์ (Keyboard obscuring inputs) ✅ เสร็จแล้ว
**ปัญหา:** 
ในฟอร์มแจ้งปัญหา (ตอนพิมพ์รายละเอียด) หรือในช่องค้นหาบนมือถือ เมื่อผู้ใช้แตะเพื่อพิมพ์ คีย์บอร์ดจำลองจะเด้งขึ้นมาบังช่องกรอกข้อมูลหรือปุ่ม "ส่งรายงาน" ด้านล่าง ทำให้ต้องปัดหน้าจอเพื่อหาปุ่ม หรือมองไม่เห็นว่าตัวเองกำลังพิมพ์อะไรอยู่

**แนวทางการแก้ไข:**
- เพิ่มพื้นที่ว่างด้านล่างสุดของฟอร์ม (Bottom Padding) เผื่อระยะคีย์บอร์ด
- ตรวจสอบให้แน่ใจว่าช่องกรอกข้อมูล (Input/Textarea) จะเลื่อนขึ้นมาให้อยู่เหนือคีย์บอร์ดอัตโนมัติ (Scroll into view)
- ซ่อนแถบเมนูด้านล่าง (ถ้ามี Bottom Navigation) อัตโนมัติเมื่อคีย์บอร์ดเด้งขึ้นมา เพื่อเพิ่มพื้นที่แสดงผล

---

### 11. ขนาดปุ่มและระยะห่าง (Touch Targets) แคบเกินไป ✅ เสร็จแล้ว
**ปัญหา:** 
ปุ่มต่างๆ เช่น ปุ่ม Pagination (เลขหน้า), ไอคอนลบ/แก้ไข, หรือหมุดบนแผนที่ อาจมีขนาดเล็กและอยู่ชิดกันมากเกินไป ทำให้ผู้ใช้งานแตะพลาดไปโดนปุ่มข้างๆ ได้ง่ายมากบนมือถือ

**แนวทางการแก้ไข:**
- ขยายขนาดปุ่มและพื้นที่ที่สามารถแตะได้ (Touch Area) ให้มีขนาดอย่างน้อย 44x44 pixels (ตามมาตรฐานการออกแบบ UI มือถือ)
- เพิ่มระยะห่าง (Gap/Margin) ระหว่างปุ่มไอคอนที่อยู่ติดกัน โดยเฉพาะปุ่มที่ทำงานตรงข้ามกัน (เช่น ปุ่มยกเลิก และ ปุ่มยืนยัน) ให้อยู่ห่างกันพอสมควรเพื่อป้องกันการกดผิด

---

### 12. การรองรับขอบจอและรอยบาก (Safe Area & Notch) ✅ เสร็จแล้ว
**ปัญหา:** 
มือถือยุคใหม่ (โดยเฉพาะ iPhone) จะมีรอยบาก (Notch) ด้านบน และแถบ Home Indicator ด้านล่าง หากไม่ได้ตั้งค่าเผื่อระยะไว้ แถบเมนูด้านล่างสุด (`MobileBottomNav`) หรือ Header อาจจะไปทับซ้อนกับ UI ของระบบปฏิบัติการ ทำให้กดยากหรือดูไม่สวยงาม

**แนวทางการแก้ไข:**
- ใช้ตัวแปร CSS ของระบบมือถือ เช่น `padding-bottom: env(safe-area-inset-bottom)` กับแถบเมนูด้านล่าง
- ตั้งค่า `<meta name="viewport" content="... viewport-fit=cover">` ในหน้า `index.html` เพื่อให้หน้าเว็บขยายไปถึงขอบจออย่างปลอดภัย

---

### 13. ฟังก์ชันดึงเพื่อรีเฟรช (Pull-to-Refresh) ✅ เสร็จแล้ว
**ปัญหา:** 
พฤติกรรมความเคยชินของผู้ใช้มือถือเวลาต้องการอัปเดตข้อมูล (เช่น ดูว่ารายงานซ่อมเสร็จหรือยัง) คือการ "ดึงหน้าจอลงจากขอบบน" (Pull-to-Refresh) แต่ในแอปเว็บทั่วไปหากไม่ทำไว้ ผู้ใช้อาจจะต้องกดปุ่มรีเฟรชเบราว์เซอร์เองซึ่งไม่สะดวก

**แนวทางการแก้ไข:**
- เพิ่ม Component สำหรับทำ Pull-to-Refresh หุ้มรอบหน้า Dashboard และหน้ารายงาน เพื่อให้การอัปเดตข้อมูลเป็นธรรมชาติเหมือนกำลังใช้แอปพลิเคชันมือถือจริงๆ

---

### 14. โหลดข้อมูลมากเกินไปบนมือถือ (Data Fetching Performance) ✅ เสร็จแล้ว
**ปัญหา:** 
ในโค้ดมีการตั้งค่าดึงข้อมูลมารวดเดียว 100 รายการ (เช่น `fetchReports(1, 100)`) หากมีผู้ใช้งานหรือข้อมูลเยอะขึ้น การโหลดข้อมูลจำนวนมากบนมือถือจะกินอินเทอร์เน็ต (Data) กินแบตเตอรี่ และทำให้แอปหน่วง (เครื่องร้อน)

**แนวทางการแก้ไข:**
- ปรับไปใช้ **Server-Side Pagination** ผสมกับ **Infinite Scroll** (เลื่อนลงสุดแล้วค่อยโหลดเพิ่มทีละ 10-20 รายการ)
- หรือทำเป็นปุ่ม "โหลดเพิ่มเติม" แทนการดึงข้อมูลมาทั้งหมด 100 รายการพร้อมกันตั้งแต่แรก

---

### 15. ปัญหาซ่อนข้อมูลสำคัญใน Tooltip (Hover ไม่ทำงานบนมือถือ) ✅ เสร็จแล้ว
**ปัญหา:** 
ในฝั่ง Admin มีการใช้ `Tooltip` (เอาเมาส์ชี้แล้วมีข้อความเด้ง) ค่อนข้างเยอะ ซึ่งบนมือถือไม่มี "เมาส์" ผู้ใช้ต้องใช้วิธี "แตะ" ซึ่งอาจจะไปเผลอกดปุ่มนั้นแทนที่จะได้อ่านข้อความ

**แนวทางการแก้ไข:**
- เปลี่ยน Tooltip บนมือถือเป็นการแสดงข้อความไว้ข้างใต้เลย 
- หรือใช้ปุ่มไอคอน `(i)` แล้วพอกดให้เด้ง Modal/Bottom Sheet อธิบายข้อมูลแทน

---

### 16. ปัญหาค้างสถานะ Hover บนปุ่ม (Sticky Hover) ✅ เสร็จแล้ว
**ปัญหา:** 
ปุ่มต่างๆ ที่มีการใส่สไตล์ `hover:bg-...` บนมือถือเวลากด (Tap) ปุ่มมันจะเปลี่ยนสี แต่พอยกนิ้วออก ปุ่มมักจะค้างสีนั้นไว้ไม่ยอมเปลี่ยนกลับ ทำให้ผู้ใช้สับสนว่าปุ่มกำลังทำงานหรือค้าง

**แนวทางการแก้ไข:**
- ในมือถือควรเน้นใช้ `active:` (เปลี่ยนสีเฉพาะตอนนิ้วแตะ) แทน `hover:` เพื่อให้เกิดการตอบสนอง (Tactile feedback) แบบแอปมือถือจริงๆ 
- ใช้ CSS Media Query `@media (hover: hover)` เพื่อจำกัดให้ hover ทำงานเฉพาะบน Desktop

---

### 17. ตารางข้อมูล (Table) ใช้งานยากบนมือถือ ✅ เสร็จแล้ว
**ปัญหา:** 
หน้าที่มีตารางเยอะๆ ของฝั่งแอดมิน แม้จะสามารถเลื่อนซ้ายขวาได้ แต่ผู้ใช้มือถือมักไม่รู้ว่ามันเลื่อนได้ (เพราะ Scrollbar ซ่อนตัวอัตโนมัติบน iOS/Android)

**แนวทางการแก้ไข:**
- ถ้าจำเป็นต้องใช้ตารางบนมือถือ ควรมีไอคอนลูกศรบอกว่า "ปัดซ้ายขวาเพื่อดูเพิ่มเติม" 
- หรือบังคับแปลงตารางให้กลายเป็น Card View ทั้งหมดในจอเล็ก (ใช้ Grid แทน Table)

---

### 18. รูปแบบแจ้งเตือน (Alert/Toast) ขวางหน้าจอ ✅ เสร็จแล้ว
**ปัญหา:** 
การใช้ระบบแจ้งเตือนอย่าง `SweetAlert2 (Swal)` มักจะเด้งตรงกลางจอ หรือแจ้งเตือน (Toast) ที่เด้งมุมขวาบน จะกดปิดยากบนมือถือ และมักจะถูกคีย์บอร์ดบัง

**แนวทางการแก้ไข:**
- เปลี่ยนการแจ้งเตือนบนมือถือให้เป็นแบบ **Snackbar (เด้งจากขอบล่างของจอขึ้นมานิดนึง)** จะอยู่ใกล้นิ้วโป้ง และไม่รบกวนสายตาเท่าตรงกลางจอ

---

### 19. UI ค้างหรือหน่วงตอนอัปโหลดรูปความละเอียดสูง ✅ เสร็จแล้ว
**ปัญหา:** 
ถึงแม้แอปจะมีการบีบอัดรูป (Image Compression) ก่อนส่ง แต่กล้องมือถือสมัยใหม่ไฟล์ใหญ่มาก (5-10MB) ตอนแอปทำการบีบอัด หน้าจออาจจะดูเหมือน "ค้าง" ไปชั่วขณะ

**แนวทางการแก้ไข:**
- ทันทีที่ผู้ใช้เลือกรูปจากอัลบั้ม ควรมี Loading แบบเต็มหน้าจอหรือ Overlay พร้อมข้อความว่า *"กำลังเตรียมรูปภาพ..."* เพื่อไม่ให้ผู้ใช้ตกใจแล้วเผลอกดปุ่มอื่นซ้ำ

---

### 20. ขาดประสบการณ์แอปแบบเต็มจอ (PWA - Add to Home Screen) ✅ เสร็จแล้ว
**ปัญหา:** 
ระบบแจ้งปัญหาซ่อมถนนเป็นแอปที่มักจะถูกใช้ข้างนอกสถานที่ หากเปิดผ่านเบราว์เซอร์ปกติจะมีแถบ URL คอยกวนใจและเสียพื้นที่หน้าจอ

**แนวทางการแก้ไข:**
- เพิ่มไฟล์ `manifest.json` เพื่อทำระบบให้เป็น PWA (Progressive Web App) ผู้ใช้จะสามารถกด "เพิ่มลงหน้าจอโฮม" แล้วเปิดใช้งานได้เหมือนแอปพลิเคชันจริงๆ (เต็มจอ ไม่มีแถบ URL)
